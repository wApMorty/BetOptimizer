1. Protocole

Un Elo général et un Elo par surface, mélangés avec un poids {{ frozen.surface_weight|num(2) }} pour la surface ; K(n) = {{ frozen.k_base|num(0) }} / (n + 5)^{{ frozen.k_shape|num(1) }} avec n le nombre de matchs déjà joués. Chaque jour, les prévisions précèdent les mises à jour : aucune fuite du futur. Les forfaits sont ignorés ; les abandons sont prévus mais ne modifient pas les classements.

Configuration choisie sur la validation (2022-2023, {{ frozen.validation_matches }} matchs, log loss {{ frozen.validation_log_loss|num(4) }}) parmi {{ frozen.configs_tried }} configurations, en {{ frozen.sessions }} session(s) de réglage, puis gelée avant la lecture du test.

Le test compte {{ test_matches }} matchs à partir du {{ test_start }} ; {{ test_scored }} sont terminés avec deux joueurs installés (au moins 10 matchs vus) ; {{ test_with_market }} ont une cote Pinnacle et servent à la comparaison.

3. Le modèle apporte-t-il quelque chose au marché ?

On mélange les deux dans l'espace logit : σ((1 − w)·logit(marché) + w·logit(Elo)). Le poids w est choisi sur la validation ({{ info.validation_matches }} matchs), puis lu sur le test. Si le meilleur poids est 0, l'Elo ne sait rien que le marché ignore.

Limites

  • Pas de CLV, pas de décision d'avant-match. Les cotes de tennis-data sont quasiment des clôtures : on compare des probabilités au marché final, on ne simule aucun pari. Seule l'archive en direct, qui sépare prix d'avant-match et clôture, permettra de juger un avantage.
  • Joueurs identifiés par leur nom publié. Deux homonymes se confondent dans le classement (voir edge tennis check). Le détecteur ne voit que les homonymes qui jouent le même jour.
  • Format ignoré. L'Elo ne distingue pas le meilleur des 3 du meilleur des 5, où le favori gagne plus souvent : lire la tranche « au meilleur des 5 ».
  • Réglage. {{ frozen.configs_tried }} configurations essayées sur la validation : le test, lui, n'a servi qu'à ce rapport.
